## 2 · 走查中额外抓到并当场修掉的两个

**2.1 我把写锁拆成两把，删除必然自死锁。** 为了复用同一份日志，我把 `AppState` 改成
`trash = TrashManager(paths:lock:log: opLog)`，但没共用 `WriteLock`——TrashManager 持自己那把锁搬文件，
再调 opLog 那把锁写日志，同一文件两个 fd 的 flock 在同进程里也互斥，删除直接卡到超时。
真机上表现为「删除失败：WriteLock.LockError」。**这条恰好是修 2 把它照出来的**——旧代码里它已经发生，只是没人看得见。
修法：App 全进程一把 `WriteLock`，`OperationLog` / `TrashManager` / `AssemblyService` 共用；
`AssemblyService.init` 加可注入 `lock`（默认 nil 自建，CLI 与测试不受影响）。
回归测试：`ItemChangeLedgerTests.sharedWriteLockMakesDeleteLeaveCompleteLog`（删除落日志 + manifest 记审计锚点 + 恢复往返）。

**2.2 diff Sheet 的「重新加载」是坏的出口。** 原写法 `app.rescan(); app.refreshDiffStaleness()`——
重扫是异步的，比对永远发生在索引还没落定的一瞬间。改成 `reloadDiff()`：请求重扫并置 `reloadingDiff`，
由 `finishRescan()` / 三段式扫描结束时补一次比对；期间文案转「正在按已知位置重扫，扫完再比对…」+ spinner。

## 4 · 走查新抓到的四个问题（要裁决，我没动）

**D13 · 临时目录进了全集，且 App 与 CLI 的"全集"不是同一份。**
证据：清单里 `agent-browser-verify` 显示「用户级 · Codex · 1 次」，但 `skillctl info agent-browser-verify` 报 not-found；
真实路径是 `~/.codex/.tmp/plugins/plugins/vercel/skills/agent-browser-verify`。
后果很直接：**人在 App 里看得见的东西，Agent 用 CLI 拉不到**——装配闭环从这一条就断了。
建议：`.tmp` / `*/.tmp/*` 归入剪枝类别（设置页逐项可勾选，与既有 9 类同构），并加一条"App 全集 ⊇ CLI 全集"的一致性断言测试。
影响面：条目总数与所有以条目数为口径的数字会下降 → 属口径变更，旧计数作废。

**D14 · 删除失败会留下半态。** 2.1 那次超时之后检查磁盘：文件**已经**搬进回收站、manifest 已写，
但操作日志里没有那条删除（`manifest.logRecordId` 为空）。也就是「三步齐」不是原子的，
而 UI 当时说的是"删除失败"。触发条件不止锁——磁盘满、权限、搬运中途失败都会。
建议三选一：(A) 日志写失败就把已搬的落点搬回去（全有或全无）；(B) 先写 pending 日志再搬，收尾改写结果；
(C) 允许半态但回执必须说清"已移入回收站、日志未记"。我倾向 A（对用户最好读，且恢复按钮不撒谎）。

**D15 · G3 的「快照过期」在真机上常态触发，验收因此不可达。**
清单完全落定（1973 Skills、CPU 归零）后重开 diff Sheet，仍判「清单已更新」，「关闭并验收」一直禁用；
修好 2.2 的出口之前，人没有任何办法完成验收。根因方向：`revision` 是**整盘清单条目 id 的哈希**，
而"验收期间清单又变了"本意是"这次装配的结果被后来的动作改掉了"——用全盘哈希做判据，
任何一处无关目录的变动（`.tmp` 抖动、别家 Agent 装了东西）都会锁死验收。
建议：把快照范围收到**该事件影响的项目 / Agent 子集**，或改成"记录事件之后又发生的变动清单，让人看着决定"。
这条动的是 PRD G3 的裁定，我不擅自改。

**D16 · 重扫期间 headline 数字会缩水再涨回。** 真机观测：1973 → 1834 → 1398 → 1767 → 1973，
期间页头与汇总条一路变。根因是重扫"清空累积器再逐批重建"，而数字本身是产品对外的第一句话。
建议：重扫期间保留上一版全量数字并标注「索引持续更新中」，新数字只在**超过**旧值时替换（或干脆双数并列：已扫 N / 上次全量 M）。
