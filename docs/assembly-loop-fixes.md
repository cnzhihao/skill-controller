## 1 · D15：验收在真机上不可达

**根因**：`revision` 是整盘清单条目 id 的 FNV 哈希。G3 想表达的是"这次装配的结果在验收前又被改了"，
但全盘哈希会把**任何一处无关变动**（别家 Agent 装了东西、某个临时目录多出一列）也算成"这次过期了"。
真机表现：清单完全落定（1973 Skills、CPU 归零）后重开 diff Sheet，仍判「清单已更新」，
「关闭并验收」永久禁用——人在这套系统里唯一的动作做不了。

**改法**：
- 快照口径收到影响面：`revision(of:within:)` 只哈希落在 `affectedDirs` 内的条目；
  `affectedDirs` = 项目根 + 每个落点所在目录。
- App 侧 `refreshDiffStaleness()` 改用 `currentRevision(within: event.revisionScope)`。
- 旧事件（`revisionScope == nil`）持全盘口径、与新口径不可比 → **不再拿它锁人**（宁可放行，也不用一把永远解不开的锁）。
- `revisionScope` 声明为**可选**：给已持久化的 Codable 快照加非可选字段会让整份事件文件解码失败，
  已有的待验收 Banner 会凭空消失。

**踩到的一层**：新增测试里"影响面内变动应该锁"这条一开始直接失败。根因是 macOS 的
`/var → /private/var` 根软链——`affectedDirs` 给的是 `/var/...`，索引里的落点是 `/private/var/...`，
字符串前缀比较漏判。真机上等价场景是**项目目录本身是一棵软链**。
修法：所有参与比较的路径统一过 `pathKey()`（canonical + standardized），
`affectedDirs` 存的也必须是同一口径，否则写进事件文件的快照和运行时算的永远对不上。

## 2 · D13：App 看得见、CLI 拉不到

**真机定位到的根因不是扫描逻辑**：同源码新编的 CLI 能 `info agent-browser-verify`，
PATH 上那个前一天装的二进制拉不到——而**两边都自称 0.2.0**。版本号在 `main.swift` 里写死一份、
core 里又有一份，旧二进制无从分辨，于是我把一次装错东西误判成了扫描 bug。

**改法**：
- 版本只留一处真相：`main.swift` 读 `SkillControllerVersion.string`，本次升到 **0.2.1**。
- App 写发现缓存时真的带上 `builderVersion`（此前那个字段一直是 nil，所以"版本不符就警告"的逻辑永远不触发）。
- CLI 读到非同一次构建的缓存 → 如实警告"两者不是同一次构建，请重装 skillctl 或重新扫描全盘"；
  没有缓存走 home 两层兜底时 → 自述"这份全集比 App 里看到的少"。**降级不许静默**。
- README 补：改过扫描口径必须重装 skillctl；本机 `/usr/local/bin` 不可写，装到 `~/.local/bin`。

## 3 · 度量结论：`.tmp` 不是"几条杂项"，是清单的三分之一

按当前发现缓存离线统计（`scan-scope-cache.json` + 实际目录内容）：

| 量 | 数值 |
| --- | --- |
| 位置总数 | 1,105 |
| 含 `.tmp` / `.temp` 的位置 | 174（skills 目录 130、MCP 文件 44） |
| 剪掉后位置数 | 931 |
| 受影响**落点** | 约 1,094 处 |
| 只存在于 `.tmp` 的 skill 名 | **628 个** |
| 剪掉后清单条目数（预估） | 1,973 → **约 1,345** |

举例：`agent-browser-verify`、`adobe-batch-edit-photos`、`adobe-create-mockups` 等一整批
都只活在 `~/.codex/.tmp/bundled-marketplaces/openai-bundled/plugins/*/skills/` 里——
那是 Codex 解包自带 marketplace 的临时检出，随工具重启重置，不是任何人的挂载位。

> **口径变更声明**：`temp` 剪枝类别默认勾选，下一次全盘重扫后条目数与所有以条目数为口径的数字
> （1,973 这个 headline、各家 Agent 的挂载数、被挂/落点总数）都会显著下降。
> 这是**度量口径变化，不是成果**：此前所有以旧口径记录的计数（含 R1 采集表基线与
> `inventory-filter-redesign.md` 里的 1970/5049 系列数字）与新数字**不可比**，R1 基线自本次起重测。
> 下表 628 / 1,345 是改前离线预估；**真机重扫后的权威数以 §5 为准**（实测 1,346）。

顺带：D12（`references` / `scripts` 被当独立 skill）与这条同源——都是收录判定过宽，
两条都落地后条目数还会再降一截。

## 4 · 测试

`swift test` 69 项全绿（本轮新增/重写 5 项）：
- `revisionIsScopedToAffectedDirs`：影响面外变动不锁、影响面内变动要锁、跨实例哈希一致
- `affectedDirsCoversProjectAndLandingParents`：影响面 = 项目根 + 落点父目录，同目录不重复计
- `cliWarnsWhenCacheCameFromAnotherBuild`：版本不符要警告；无缓存兜底要自述"比 App 少"
- `tempCheckoutsAreNotMountPoints`：`.tmp` 不被收进位置清单，且跳过数可报、取消勾选能收回
- `sameCacheYieldsSameItemsOnBothSides`：同一份缓存下 App 侧与 CLI 侧条目集合必须相等

`xcodebuild clean build` 绿。

## 6 · 真机复验又抓到两件（待裁决）

**D17 · 设置里存的是"显式剪枝列表"，导致以后新增的剪枝类别对老用户默认不生效。**
现象：`settings.json` 里 `prunedCategories` 是一份写死的数组（本次走查前不含 `temp`），
而 `AppSettings.discoveryRules` 只在它为 `nil` 时才用 `.standard` 默认集——
于是第一次启动时「临时检出目录」是**未勾选**的，`.tmp` 那 628 个条目照旧进清单，
缓存也被判定"规则一致"而直接沿用（首屏就是 1973）。全新安装没问题，**碰过任何一个开关的人会被钉在旧默认集上**。
建议：改成存"对默认值的逐项覆盖"（`overrides: [category: Bool]`），有效集 = 默认 ⊕ 覆盖；
这样新增类别对所有人生效，且每个人的显式改动仍然保留。属数据迁移 + 设置语义变更，等拍板。

**D18 · 删除成功没有任何回执。** 上一轮提交标题写的是「写操作结果一律上屏」，实测**只对了一半**：
恢复有回执、失败有回执，但删除成功后只有"行消失"这一件事。删除是不可逆感最强的动作，
用户应当当场看到一句"已移入回收站 · 30 天内可一步恢复 + 去回退页"。
修法很小（复用 `WriteOutcomeBanner`，`deleteItem` 成功分支写一条中性回执），
但它是上一条提交说明的兑现，不是新功能。
