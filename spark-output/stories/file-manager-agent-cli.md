## Story 1 · 打开就满：一眼看清全盘 Skill 归属

- **Persona**：智昊，设计师，重度多 Agent 用户
- **JTBD**：当智昊想搞清楚这台电脑上到底有哪些 Skill、分别被谁挂着时，他想打开 App 第一秒就看到按 Agent × 层级 × 项目归好类的全盘清单，从而 30 秒内答出归属。
- **关联策略维度**：信息架构 IA
- **优先级**：P0

**Story 主体**：

作为智昊，
智昊想要 App 第一次启动就自动扫完全盘、不问他任何一个配置问题就呈现清单，
从而他再也不用翻文件夹和跑 find。

**这个 Story 在用户那一侧长什么样**：

双击打开 → 首页已经是满的，按 Agent 分组、每组再分用户级和各项目 → 智昊扫一眼就说出"docx 这个我三个 Agent 都挂着" → 合上电脑，心里踏实。

**这个 Story 算完成的标准**：

- 冷启动 ≤5s 出首版清单，全程零配置问答
- 任一 Skill 能直接答出：归属 Agent、用户级/项目级、所属项目
- 同名 Skill 多副本合并为一个条目，并列显示各落点
- 新机器/无权限异常有明确提示，不出现空白页

**设计触点**：

- 涉及屏：全盘清单首页 / 归属详情抽屉
- 涉及组件：三级分组树、全局搜索、归属徽章
- 涉及状态：扫描中 / 满盘 / 空（新机） / 错误（权限）
- 涉及交互模式：文件管理器式浏览

**测试的假设**：n/a（地基能力）

**我的诚实看法**：这是竞品杀成红海的地方——按"能用即可"做，一点都别打磨，差异化全在 2/3/5。

**参考产品**：chrlsio/agent-skills 的浏览面板轻量可借鉴，但它的空启动正是反面教材。

## Story 2 · 新项目一条命令：Agent 自己来拉 Skill ⭐

- **Persona**：智昊
- **JTBD**：当智昊开了新项目需要一套匹配业务场景的 Skill 时，他想对 Agent 说一句"按这个项目把它配齐"，Agent 就自己经 CLI 拉取落位，从而他从此不手工装任何东西。
- **关联策略维度**：交互设计
- **优先级**：P0
- **关键假设标记**：⭐（本 Story 就是"Agent 自装配靠谱"的 dogfooding 场景）

**Story 主体**：

作为智昊，
智昊想要新项目里的 Agent 通过一条 CLI 命令自己查询 Skill 全集、按需拉取落位，
从而装配从半天手抄变成一个口头的瞬间。

**这个 Story 在用户那一侧长什么样**：

智昊对新项目的 Agent 说"按这项目的业务把技能配好" → Agent 自己跑 CLI 查全集、挑了一套装上 → 第二天智昊打开清单，项目层级下整整齐齐一排新条目，来源清清楚楚 → 他什么都没管。

**这个 Story 算完成的标准**：

- Agent 经一条 CLI 命令完成"查询 + 拉取 + 落位"
- 全程不需要智昊点一次确认
- 次日清单里能看到 Agent 带来了哪些、分别来自哪
- 拉取失败（冲突/写不进）在清单上留明确痕迹，不静默

**设计触点**：

- 涉及屏：项目详情（挂载列表 + 来源）/ 清单 diff 状态
- 涉及组件：面向 Agent 的 CLI（查/拉）
- 涉及状态：初始 / 装配成功后 / 失败
- 涉及交互模式：agent-tool 接口

**测试的假设**：⭐ Agent 能靠谱地按业务场景自主装配——产品命门假设，本 Story 即验证场。

**我的诚实看法**：这个假设砸了，产品整体退回"人管清单"的老路——先 dogfood 它，别的都可以等。

## Story 3 · Agent 自己挂、自己卸，保住最小集合 ⭐

- **Persona**：智昊
- **JTBD**：当日常使用中发现某 Agent 挂载集又开始膨胀时，智昊想让它自己经 CLI 挂上需要的、卸掉不用的，从而每个 Agent 长期停在最小高信号集合。
- **关联策略维度**：交互设计
- **优先级**：P1
- **关键假设标记**：⭐

**Story 主体**：

作为智昊，
智昊想要每个 Agent 能对自己的挂载集合做增删（挂上/卸下，经 CLI 写回目录），
从而不用定期人肉瘦身。

**这个 Story 在用户那一侧长什么样**：

Agent 发现某次任务需要 file-translate → 自己经 CLI 挂上 → 用完判断低频，自己卸下 → 智昊在清单上只看到"生效集合一直很小"，过程零参与。

**这个 Story 算完成的标准**：

- Agent 可对指定目标（自己或其他 Agent）挂载/卸载指定 Skill
- 卸载 ≠ 消失：Skill 留在全集，随时可回挂
- 每个 Agent 当前生效集合在清单一屏可见

**设计触点**：

- 涉及屏：Agent 视图（已挂/未挂）
- 涉及组件：CLI 挂/卸命令、挂载状态徽章
- 涉及状态：切换成功 / 目标目录不存在 / 无权限
- 涉及交互模式：agent-tool 接口

**测试的假设**：⭐ 同 Story 2，但专测"写回别的 Agent 目录"这一最危险侧面。

**我的诚实看法**：各 Agent 的目录与权限模型不统一（Codex、Claude、QoderWork 各家一套）是最大实现坑，PRD 前必须逐个侦查一遍。

## Story 4 · 看错了也能一步撤回：删除与操作日志

- **Persona**：智昊
- **JTBD**：当智昊或他的 Agent 做错一次挂/删时，他想一步恢复原样并查清是谁干的，从而放心把管理权整个交出去。
- **关联策略维度**：交互设计
- **优先级**：P1

**Story 主体**：

作为智昊，
智昊想要每一次读写都进日志、每一个删除都能一步撤销，
从而即使 Agent 犯浑，损失也只是几分钟。

**这个 Story 在用户那一侧长什么样**：

清单上某个 Skill 变灰（被某 Agent 卸载了）→ 智昊点开日志：三小时前，Codex 的项目挂载动作 → 点"恢复" → 磁盘回来了，全程不超过十秒。

**这个 Story 算完成的标准**：

- GUI 动作封顶两个：删除、恢复
- 日志可按时间/按 Agent 查每一次读写
- 一步撤销后磁盘状态与操作前一致
- 回收站保留 ≥30 天

**设计触点**：

- 涉及屏：操作日志流 / 回收站
- 涉及组件：撤销按钮、时间线列表
- 涉及状态：初始 / 成功 / 目标已被二次删除
- 涉及交互模式：文件版本式回滚

**测试的假设**：押"误操作频率低到日志+回收站足以兜底"。

**我的诚实看法**：保留窗口宁长勿短——30 天起，后期砍容易、补很难。

## Story 5 · 账本：谁在用什么、用了多少

> **修订（2026-09-19 · Sitemap 阶段）**：文件管理器观测不到"调用"（装载 ≠ 调用），用户拍板**工具拿不到的信息不做**——调用层/会话解析器整段砍掉。本 Story 收敛为**挂载账**：90 天挂载变动、零挂载清单、基于 SKILL.md 文案的静态触发词重叠并列。正式版以 stories.json 中的 story-5 为准，下方原文保留作决策痕迹。

- **Persona**：智昊
- **JTBD**：当季度末想给用户级瘦身时，智昊想要真实使用频次给他壮胆，但工具别替他下判断，从而删得心安。
- **关联策略维度**：数据可视化
- **优先级**：P1

**Story 主体**：

作为智昊，
智昊想要 App 记录每个 Skill 被谁、多频繁地挂载与调用，并零观点地摆出来，
从而瘦身决策由数据而不是恐惧驱动。

**这个 Story 在用户那一侧长什么样**：

智昊点开用户级清单按频次排序 → 尾部 600 个"近 90 天零挂载"的条目安静列着 → 没有红色警告、没有"建议删除" → 他自己框选、删除，删完心里有底。

**这个 Story 算完成的标准**：

- 每个 Skill 显示按 Agent 分的近 30 天频次
- 触发词重叠对并列标注（谁跟谁可能打架）
- 不出现建议、评分、警告色——只摆数
- 零频条目在排序下一眼可数

**设计触点**：

- 涉及屏：Skill 详情（频次区）/ 重叠对并列标注
- 涉及组件：迷你柱状图、零频清单
- 涉及状态：数据稀疏 / 数据充足
- 涉及交互模式：只读看板

**测试的假设**：频次低 ≠ 无价值——账本解读必须克制（低频但关键的季节性 Skill 会误伤）。

**我的诚实看法**：这个 Story 最难的是自律。图一画出来，加"建议删"的诱惑就来了；零观点恰恰是这产品和所有竞品的分界线，别破。

## Story 6 · MCP 也是清单里的一等公民

- **Persona**：智昊
- **JTBD**：当智昊要给某 Agent 增删 MCP server 时，他想让 MCP 和 Skill 在同一张清单里同构管理，从而不用为第二类产品再装一个工具。
- **关联策略维度**：信息架构 IA
- **优先级**：P2

**Story 主体**：

作为智昊，
智昊想要清单把 MCP 配置项作为第二类对象并列展示，且增删也走工具与 CLI，
从而一个控制器管住两类装配对象。

**这个 Story 在用户那一侧长什么样**：

清单顶部切到"MCP"类型 → 每个 Agent 挂了哪些 server、在用户级还是项目级一目了然 → 智昊说"给 Codex 加上这个 server"，Agent 经 CLI 写进它的 JSON，智昊没碰过花括号。

**这个 Story 算完成的标准**：

- 两类对象（Skill/MCP）并列，归属三维一致
- 增删全走工具/CLI，人不手编 JSON
- 写回保持该 Agent 原生格式，写前自动备份

**设计触点**：

- 涉及屏：清单对象类型筛选
- 涉及组件：JSON 条目卡、CLI 挂/卸命令（MCP 变体）
- 涉及状态：写入成功 / 格式解析失败
- 涉及交互模式：agent-tool 接口

**测试的假设**：n/a

**我的诚实看法**：优先级放 P2 对，但"两类对象的统一数据模型"必须 v1 就定死，否则 Story 6 落地那天就是清单重构日。
