# Story-5 · 挂载账（Ledger）范围与待定设计点

- 状态：**未开工**（按合同「Phase 3 之后停」，等 R1 验证环回填后由人决定）
- 定位：PRD §6.5 / stories.json story-5（P1）/ edge G6（page-ledger）
- 一句话：**把文件层已发生的挂载事实攒成只读账本，给"敢不敢删 Skill"壮胆——只摆数，绝不替用户判断。**

---

## 一、它是什么 / 为什么存在

智昊想给用户级 Skill 瘦身却不敢下手，因为"万一有用呢"。挂载账提供**文件层可观测的事实**（谁挂了、挂了多久、谁从没被挂过、谁的触发词在文案上撞车），把删/留决策的依据摆出来——但**不给任何"建议删除"的结论**（零观点红线）。它是 CLI 自装配天然产生的"白捡数据"，不是独立子系统。

## 二、三个视图（In Scope）

| 视图 | 摆什么 | 数据源 | 现在能不能算 |
| --- | --- | --- | --- |
| ① 变动时间线 | 近 90 天 mount/unmount/assembly 增删流水 | `operation-log.jsonl`（Phase 2 已落） | ✅ 能，缺的是"攒够天数" |
| ② 清单频次 / 零挂载清单 | 每 Skill 被哪些 Agent/项目挂、挂过几次；把"从未挂载"排到显眼处 | 清单 `mountedBy`（空 = 零挂载） | ✅ 现在就能算 |
| ③ 触发词重叠对 | 两卡并列 +「谁留谁走，你或你的 Agent 决定」 | SKILL.md 的 name+description **静态文案比对** | ❌ 需新写分析模块（见 §四待定） |

数据模型已按 types.ts 1:1 预留字段：`InventoryItem.mounts: [MountRecord]`、`triggerOverlapWith: [String]`（当前恒空）。App 侧「挂载账」入口现为诚实空态占位页。

## 三、Out of Scope（硬约束落点，写死）

1. **调用层追踪**：装载 ≠ 调用。看不到"装上后 Agent 到底调没调"，那需要解析会话日志——永久排除（工具拿不到的信息不做）。"低频"永远只指"低频被挂载"，此误差用户已明确接受。
2. **任何"低频 = 建议删"的判断**、评分、推荐按钮、高/低暗示色——出现即违反 Brief。
3. **atime / 会话日志解析器**：不做。

## 四、开工前需智昊拍板的设计空白

| # | 待定 | 选项 / 建议 |
| --- | --- | --- |
| L1 | **"触发词重叠"判定算法**（唯一需要新逻辑处） | 建议：对 name+description 做分词 → 去停用词 → 取关键词集合 → Jaccard 相似度 ≥ 阈值算一对。阈值/分词粒度需定；纯本地、无网络 |
| L2 | 重叠比对范围 | 全局两两（千级 Skill 下 O(n²) 要控性能）vs 仅同 Agent 生效集内。建议后者起步，性能可控且更贴"会打架"的真实场景 |
| L3 | 时间线粒度 | 按天聚合 vs 逐条事件。建议按天折叠 + 展开逐条（对齐回退页 boundary-long-log 的按日分组） |
| L4 | 数据窗口 | PRD 说"近 90 天"；不足 90 天时表头标实际天数（如"仅 5 天数据"），不做高低暗示 |

## 五、edge 规格（must/should，实现时逐态对照）

- `empty-first-day`（must）：顶部一次性说明条"账本从 {安装日} 起记录，此前的挂载无从得知" + "以下数字只反映安装之后的挂载"。
- `boundary-sparse`（should）：记录 < 7 天 → 表头注"仅 N 天数据"，无高低暗示色。
- `loading-aggregate`（nice）：90 天聚合本地 < 200ms 可不做加载态。
- 全页检查：无 destructive/警告色、无评分、无推荐按钮。

## 六、验收标准（PRD §6.5 GWT，开工后逐条对账）

1. 数据不足 90 天 → 顶部说明条 + 表头实际天数 + 无暗示色。
2. 静态比对发现 docx 与 document-writer 触发词重叠 → 详情两卡并列 +「谁留谁走，你或你的 Agent 决定」。
3. 全页零观点自检通过（Check 已把此列为基线）。
