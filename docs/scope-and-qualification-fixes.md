# D17 / D12 / D18 / D3 整改（2026-09-22 晚）

> 智昊定的顺序：D17 → D12 → D18+D3。本文记录改法、真机数据、以及一个我替他做了取舍决定的地方。

## D17 · 扫描范围设置改存「默认 ⊕ 逐项覆盖」

**问题**：`AppSettings.prunedCategories` 是一份**绝对列表**，`discoveryRules` 只在它为 nil 时才用默认集。
后果是"这个类别被关掉了"和"这个类别当时还不存在"在文件里长得一模一样——
以后每新增一个剪枝类别，对所有碰过任何一个开关的老用户都默认不生效。
D13 那次真机实测就是这么中招的：勾选前 `.tmp` 的 628 个条目照旧进清单，缓存还被判定"规则一致"直接沿用。

**改法**：新增 `prunedOverrides: [String: Bool]`，有效集 = 默认 ⊕ 覆盖；
`setPrunedCategories` 只把**与默认不一致**的项落盘（等于默认的项不落，保持跟随默认）。

**我替你做的一个取舍（要你看一眼）**：旧列表迁移时无法区分"关掉"与"当时不存在"，只能选一边。
我选了 **「旧列表里多出来的项 = 用户主张（保留）；缺项 = 无主张（跟随默认）」**。

- 保住的是：用户当年主动**勾上**的类别（比如把「桌面与下载」改成剪枝）不会丢。
- 丢掉的是：本次迁移之前主动**放开过**的默认剪枝类别，会被恢复成剪枝。
  代价可控——设置页每一类都带实测跳过数，一次点击就能改回。
- 反过来选另一边（缺项算关掉），则 D13 那类"新类别对老用户静默失效"会永久重演，
  而那个坑我们花了一整轮才定位到。

回归测试 4 条（`SettingsOverridesTests`）：旧列表缺新类别 → 新类别仍按默认生效；
旧列表多出的项保留 + 放开过的项恢复默认（把上面的取舍钉成断言）；
落盘只写覆盖项且旧字段不再写；全新安装 = `DiscoveryRules.standard`。

## D12 · 没有 SKILL.md 的目录不成为 skill 条目

**改法两条**（`InventoryScanner`）：
1. skills 目录**自己**含 `SKILL.md` → 它本身就是那一个 skill，名字取所属工具/连接器目录名，**不再枚举子目录**。
   （`~/.workbuddy/connectors-marketplace/connectors/<name>/skills/` 就是这种布局，本机 137 处）
2. 子目录要成为条目必须有 `SKILL.md`。**悬空 symlink 例外保留**——那是"挂上了但目标已不存在"的磁盘事实，
   不能因为读不到 manifest 就当它没发生过。

**真机前后对照**（同一份发现缓存、CLI 全集，改前 1,812 个名字 → 改后 1,809）：

- 消失 **37** 个，逐条查过内容，**没有一个是真 skill**：
  - 真垃圾：`__pycache__`（.pyc）、`assets`（js/html/md）、`guides`（.md 文档）、`index-cache`（索引 json）、`codex-primary-runtime`（空目录）、`configure-horizon`/`mcp-development`（只有 `SKILL.blade.php` 模板）
  - marketplace 的**分类目录**：`apple`、`creative`、`media`、`mlops`、`email`、`data-science`、`productivity`、`note-taking`、`autonomous-ai-agents`、`bundled`、`optional`、`connector-feishu`、`lark`、`agents`、`automation`、`hermes-ops` 等——里面是 `DESCRIPTION.md` + 若干真 skill 子目录，本身不是 skill
- 新增 **34** 个，抽查 `canva` / `dingtalk` / `emr-query` 都有完整 frontmatter（name + description），
  是改前"整目录被拆成 references/scripts 碎片、自己反而不是一条"的真 skill。
- 净变化 −3，但构成明显变干净：387 处假落点不再计入，「被挂 5052 次」这类虚高数的主要来源被拔掉。

**顺带发现（记下来不修）**：分类目录里嵌套的真 skill 两版都收不到——本机只有 1 例
（`data-science/jupyter-live-kernel`）。同层的 `apple-notes`、`imessage`、`obsidian` 等在别处也有挂载所以看得见。
要不要支持"分类目录递归下钻"属新范围，未动。

**命名口径提醒**：条目名取**目录名**，不取 frontmatter 的 `name`。
`connectors/dingtalk/skills/SKILL.md` 里写的是 `name: dws`，清单里显示 `dingtalk`。

## D18 · 删除成功上屏回执

上一轮提交标题写「写操作结果一律上屏」，实测只对一半：恢复有回执、失败有回执，
删除成功后只有"行消失"。现在 `deleteItem` 成功分支落一条中性回执，
复用 `WriteOutcomeBanner`：「「{name}」已移入回收站（{N} 个落点，{30} 天内可在「回退」页一步恢复）」，
出口仍是「知道了」；恢复动作会把它换成恢复回执。

## D3 · 消失态回填 actor

设计句式是「这条目刚刚被 {agent} 移出了清单」，此前因为查不到 actor 只能去掉槽位。
现在 `AppState` 除了记住条目 id，还记住它**上一次已知的落点路径**——
CLI 的装配记录 `target` 是项目 id，只有按落点路径才命中得到。
条目在面板开着时被移走 → 用 id + 落点再查一次日志 → 有 agent 就报名字、
本工具自己删的就说"被你移出"、**查不到就保持原来的中性说法**（不拿猜的填槽位）。

## 5 · 真机又抓到一件同类闭环断裂（D19，待裁决）

造 D3 场景时发现：夹具 `wt-d3b` 的**唯一落点**在 `~/.codex/skills/`，App 清单如实显示
「用户级 · 可激活于 Codex · 挂载 1 次」；但执行 `skillctl unmount wt-d3b --on codex` 报

```
{"command":"unmount","error":"该位置没有挂载：~/.agents/skills/wt-d3b"}
```

**根因**：扫描器按 agent-recon C2「Codex 双目录都扫、都记归属 Codex」识别挂载，
而 CLI 的 `mount`/`unmount --on codex` 只认**一个**规范目录（`~/.agents/skills`）。
后果与 D13 同族但方向更糟：**App 说"这家挂着"，Agent 自己说"我没挂、卸不掉"**——
挂载可观测与 CLI 自管两套口径不一致，`skillctl unmount` 无法卸掉一部分真实存在的挂载。

建议（要拍）：要么 CLI 的 mount/unmount 接受"该 Agent 的任一规范目录"并优先卸掉实际存在的那个，
要么在清单里把两种 Codex 目录区分标注（后者更诚实但会把"归属"变复杂）。
D3 的"报名字"分支也因此没造出场景，等这条定了再一起验。

## 6 · D19 已修（智昊拍 A 方案：CLI 认任一规范目录）

**改法**：卸下不再只看 primary，而是看**全部候选目录**——候选直接取读侧那张
`LocationClassifier.knownAgentDirs`，不再抄第二份表（两张表不一致正是 D19 的成因）。

- `MountTargets.candidates(agent:projectPath:home:indexDirs:)`：primary 恒在第一位，
  后接读侧认的其它容器目录，再接索引里该条目实际归属到这家的落点父目录。
- **写侧不变**：`mount`/`pull` 仍然只写 primary（C2 裁定的官方 USER scope），
  不能因为"别处也能读"就拿它当写入目标。
- **卸下看全部**：一次 `unmount` 会卸掉这家名下所有落点。只卸一个的话清单上仍然显示"挂着"，
  那条命令就成了半真半假。混合情形如实拆开：链接删掉、实体本体拒绝（不静默半成功、
  也不因为有一个被拒就不动另一个）。
- 表里没有的工具（thincoder / trae-cn 这类靠目录名动态归属）走第二轮：问索引要"这家实际挂在哪些目录"，
  而不是因为表里查不到就说自己没挂。
- 真的没挂过时仍然报错，但把**找过哪些目录**全列出来——只报 primary 路径正是原来误导人的地方。

## 7 · D20 扫描期间的事件不能丢（已真机复验）

**两层洞**：① 三段式扫描在跑时 `requestRescan` 裸 return，事件被丢弃；
② 更根本的是**监听器要等三段全跑完才起来**（本机 5–8 分钟），那段时间压根没在听。

改法：段 1 一落地就 `startWatching()`（段 3 收尾会用完整位置清单再起一次，`startWatching` 自带 stop）；
`requestRescan` 在扫描在跑时改记一次待办，`startScan` 收尾补一轮。

**真机复验（21:0x）**：授权后 20:37:54 往段 1 已扫过的 `~/.agents/skills/` 里塞了 `wt-d20-check`，
之后**完全不碰 App**；扫描 20:49 落定后该条目自己出现在清单里（用户级 · Codex · 挂载 1 次），
期间没有任何手动刷新、也没有靠切走再切回前台触发。

## 8 · D14 删除全有或全无（已真机复验）

**先说难听的**：`TrashManager.trash()` 里第 116 行的注释早就写着
「manifest 先写，再落日志（日志失败则整体回滚——不留半删状态）」——**代码根本没做**。
真机上那个"文件已进回收站、日志没记、UI 说删除失败"的半态就是它留下的。
注释承诺过的东西没实现，比压根没想过更糟。

**改法**：
- 落点搬运、manifest 写入、日志追加包进 `perform()`，外层 `catch` 里把**这次已经动过的落点原样放回**
  （实体 `moveItem` 回原位、symlink 按记录的 `linkTarget` 重建），再清掉半成品 entryDir，最后把原始错误抛出。
- 顺序改成：先定好日志记录 id → 写 manifest（已含 `logRecordId`）→ 追加日志。
  这样不会再出现"日志有了、manifest 没记锚点"需要二次改写 manifest 的窗口。
- 原位已被占用时**不覆盖**别人的东西；回滚自己失败时抛 `rollbackFailed(detail:)`，
  把放不回去的路径全列出来——绝不假装"什么都没发生"。
- 顺带修错误可读性：`TrashError` / `WriteLock.LockError` 都补了 `LocalizedError`。
  真机上失败回执曾显示「SkillControllerCore.WriteLock.LockError error 1」，
  那是把失败"形式上报了"而没人看得懂。

**真机复验（21:0x，注入故障 = 把 `operation-log.jsonl` 改成只读）**：
点删除 → 回执「删除失败：You don't have permission to save the file "operation-log.jsonl"…」；
核对磁盘：`~/.agents/skills/wt-d20-check/SKILL.md` 还在且 mtime 仍是创建时的 20:37（原样放回），
回收站没有新增半成品，日志里**没有**那条失败的删除记录（8 行不变）。
撤掉故障后再删同一个条目 → 成功回执「已移入回收站（1 个落点，30 天内可在「回退」页一步恢复）」，
日志这才多出那一条。两条路径都对上。

**未覆盖（诚实记账）**：`rollbackFailed` 这条分支没法从测试缝里确定性触发——
它要求"落点已搬走、原位又被别人占住"，而搬走之后原位天然是空的。
与其写一个靠线程抢时序的假测试，不如把它留在代码里并标明未测：该分支只把放不回去的路径拼进错误。

## 10 · D16 收口：重扫不再把清单拆了再拼回去（2026-09-22 晚）

**真根因不是数字算错，是发布时机。**`scan()` 每扫完 120 处位置就 `index.rebuild(from: 累积器)` 一次，
而 `requestRescan` 开头 `resetAccumulators()` 把累积器清零——于是一轮重扫的真实过程是
「把清单拆成空 → 一块一块拼回去」，页头/汇总条/设置页的位置数全程跟着抖
（真机 1,973 → 1,834 → 1,398 → 1,767 → 1,973）。
§9 那个"确认对话框被作废"是同一个洞的另一半：拼回去的中间某一版**不含当前选中的条目**，
`app.selectedItem` 当场变 nil，详情栏从 `detailContent` 切到 `vanishedState` 分支，
挂在原分支上的 `.confirmationDialog` presentation anchor 被移除 → 系统把框作废、我的点击落空。
所以这是一处根因、两个症状，不需要单独去"保护模态框"。

**改法（`AppState`）**：
- 一轮 pass 的结果先进**暂存**（`stagedLocations` / `stagedEntryCounts` / 累积器），
  展示属性只由唯一的写入口 `publish(generation:stillUpdating:)` 赋值。
- 发布时机收成一条规则（`ScanPublishPolicy`）：冷启动（上一版什么都没有）逐批发布，
  首屏该边扫边出；**手上已有一版全量时一轮 pass 只在收尾发布一次**。
  冷启动那条路里累积器只增不减，所以多次发布之间数字单调上涨，不会回头（有测试钉住）。
- 加**扫描代际号**：`beginPass()` 每轮 +1，被打断的旧 pass 在每个 await 之后复查代际，
  代际变了就地退出且不发布。此前 ⌘⇧R 打断在跑的轻量重扫时，旧 pass 会把半截索引盖到新 pass 上。
- 计时器从"只有三段式有"改成冷启动与轻量重扫共用（`startTicker`）。
  否则重扫期间 `scanElapsed` 停在上一轮的大值，「索引持续更新中」每次秒级重扫都闪一下——那是标签在撒谎。
- `InventoryIndex` 是 class，就地 rebuild 不触发 `@Published`；旧代码靠顺手改 `scopeLocations`
  等属性"捎带"刷新，现在不顺手改了，所以 `publish()` 末尾显式 `objectWillChange.send()`。

**我替你做的一个取舍（要你看一眼）**：todo 里原写的是「新数字只在**超过**旧值时替换」，
我实现的是「整版保留上一版、收尾一次替换」。理由两条——
① 只挑数字不放行会让页头与表格自相矛盾：页头说 1,973、列表只有 1,398 行、汇总条说「共 1,398 个」，
同一屏三套数，比缩水更难解释；② "只在超过时替换"会把**真实下降**也压掉
（删了 600 个条目之后重扫，页头该往下走），那等于为了好看牺牲准确性。
双数并列（已扫 N / 上次全量 M）没做：它要求人理解两个口径，而这一版根本不会出现中间态。

**连带处理**：删除成功后那一行必须当场消失。重扫改成收尾一次发布之后，
"已移入回收站"的回执上屏了、行却还能再点一次删除，那是自己造二次删除。
`InventoryIndex.removeItem(id:)` 只摘**我们自己刚写完的那一条**（计数索引同步摘掉），
重扫照跑、扫完用磁盘事实复核；别的变动一律等扫描落定，不拿猜测改索引。

**真机复验（21:28–21:49，新构建 89 测试绿 + clean build 绿）**：
- 冷启动：页头 1,446 从段 1 落定起全程不变，段 3 期间带「索引持续更新中」，扫完标签消失——
